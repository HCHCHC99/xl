# 卸粮电机控制器（UTMotVCU）业务实现对照

- 主要依据：`D:\xl\xl.xlsx`（V0.1，2026-11-04，17 个工作表，计划 146 条用例）。
- 旧用例 `水稻机卸粮系统测试用例.xlsx`（VG02 系列）仅作参考；两份文件冲突时以 `xl.xlsx` 为准。
- 代码基线：`D:\xl\vl_v.2.0.5`，从 `applications/main.c` → `boot/boot_table.c` → `applications/app_main.c` 阅读业务层。
- 角色边界（xl.xlsx `00_说明与约定`）：本工程是 **UTMotVCU，即卸粮筒回转电机控制器**。
  - 本地驱动回转电机、通过 RGV 电磁阀盒驱动升降。
  - 接收 CPB 面板按键、向 HMI 反馈状态、向 CPB 发灯帧。
  - 卸粮离合电机控制器（UnldCltchMotVCU）是**另一个选配控制器**；本工程只应做离合按键的仲裁，不应实现离合电机控制、18FF10D5 反馈或 18FFA5F0 灯帧。
- 结论性质：静态代码对照，不代表台架实测。

## 2. 从 main 看业务链路

### 2.1 启动

`main()` → `boot_run_all()` → [boot_table.c](file:///d:/xl/vl_v.2.0.5/applications/boot/boot_table.c#L167-L275)：

    storage → sys_config → mech_cfg → ctrl_mgr_init → app_hw
      → motor → foc_adc → foc_ctrl → mode → lift → swing → seq
      → ctrl_loop → ctrl_mgr_start → bg_sched → sys_voltage → eeprom
      → keyboard → vehicle → acc_state → can → can_tx → status_tx
      → led_tx → threads → tick_50ms → wdt

之后创建 `app_main`（事件驱动）和 `bg_sched`（5ms 电机/堵转）两个线程。

### 2.2 50ms 主循环

[app_main.c](file:///d:/xl/vl_v.2.0.5/applications/app_main.c#L128-L185)：

1. `lift_angle_update()`：PA7/ADC2 读举升角传感器，换算 0.1°。
2. `swing_angle_update()`：读回转编码器，换算角度、限位、零位。
3. `*_act_tick_check()`：限位/刹车到位/举升限位。
4. `mode_tick_check()`。
5. `post_event(CAN_EVT_STA_ANGLE)`。
6. `vehicle_poll()`、`acc_poll()`。

### 2.3 输入

    0x18FF8380 → hdl_panel_switch() → kb_on_can_frame()
      → 300ms 超时释放 + 同轴互斥
      → post_event(LIFT_EVT_* / SWING_EVT_* / CALIB_EVT_*)

键盘语义：[keyboard_sm.c](file:///d:/xl/vl_v.2.0.5/applications/keyboard/keyboard_sm.c#L228-L270)；同轴互斥：[keyboard_sm.c](file:///d:/xl/vl_v.2.0.5/applications/keyboard/keyboard_sm.c#L137-L193)。

两道门：

- 门 1：ACC 下电确认后拒绝“动作开始”，不拦停止（[app_main.c](file:///d:/xl/vl_v.2.0.5/applications/app_main.c#L94-L119)、[app_main.c](file:///d:/xl/vl_v.2.0.5/applications/app_main.c#L245-L253)）。
- 门 2：一键/离合必须已启车，手动四向只要求 ACC（[app_main.c](file:///d:/xl/vl_v.2.0.5/applications/app_main.c#L58-L78)、[app_main.c](file:///d:/xl/vl_v.2.0.5/applications/app_main.c#L255-L261)）。

启车判定：转速 >400rpm 或电压 >13.0V，任一连续 500ms ⇒ STARTED；CAN 静默 500ms 或电压采集缺失连续 2s ⇒ FAULT（[vehicle_control.c](file:///d:/xl/vl_v.2.0.5/applications/vehicle/vehicle_control.c#L140-L253)）。

### 2.5 一键与校准

一键设计链路：

    ONKEY → seq_control → seq_engine → SEQ_ACT_* → LIFT/SWING

实际：

- 键盘只 post `SWING_EVT_ONKEY_*`（[keyboard_sm.c](file:///d:/xl/vl_v.2.0.5/applications/keyboard/keyboard_sm.c#L242-L245)）。
- 该事件被描述表路由到 SwingControl，但回转跳转表没有 ONKEY 行（[swing_trans_table.c](file:///d:/xl/vl_v.2.0.5/applications/swing/swing_trans_table.c#L42-L107)）⇒ 被忽略。
- `seq_control_update_onekey()` 只被传入 `0,0,0`（[keyboard_sm.c](file:///d:/xl/vl_v.2.0.5/applications/keyboard/keyboard_sm.c#L267-L269)）。
- `seq_control_update()` 没有调用点；app_main 里那行是注释（[app_main.c](file:///d:/xl/vl_v.2.0.5/applications/app_main.c#L181-L183)）。

校准：键盘能产出 `CALIB_EVT_CLICK/KEY_UP`，但 app_main 对 0x3000 只留了注释，工程中没有校准业务对象（[app_main.c](file:///d:/xl/vl_v.2.0.5/applications/app_main.c#L315)）。

## 3. 模块级覆盖结论

xl.xlsx 计划 146 条，按 12 个模块统计。下表的“结论”只针对 UTMotVCU 职责范围。

| 模块 | 计划 | 当前结论 | 主要原因 |
| --- | --- | --- | --- |
| PWR 上电与启动 | 11 | 部分实现 | 启车判据/门禁/重按已实现；下电不停输出；状态帧工作模式未填 |
| MDL 机型与存储 | 9 | 大部分实现 | 13/14 齿、清除、保持、重复下发可用；11 齿编码存在协议冲突 |
| ANG 角度与限位 | 13 | 部分实现 | 举升角度可用；回转角度恒 0；角度显示未填；限位 5s 未实现 |
| MAN 手动控制 | 10 | 部分实现 | 上下可用；左右驱动断链；过零停车被禁用；5s 保持被禁用 |
| ONE 一键控制 | 17 | 未实现 | 序列配置与 xl.xlsx 时序一致，但整条链路未驱动；2s 保持/中断/超限仲裁缺失 |
| CAL 零点校准 | 13 | 未实现 | 无校准业务对象 |
| CLT 卸粮离合 | 13 | 基本不适用 | 离合电机/反馈/灯属另一个 VCU；但本机缺少离合按键仲裁 |
| PRI 优先级与互锁 | 10 | 部分实现 | 同轴互锁/手动优先已实现；一键互斥、重复触发、超限组合缺失 |
| FLT 故障检测 | 14 | 部分实现 | 阀故障可用；传感器阈值/延时不符；编码器判据不可靠；CAN 通信故障未上报 |
| COM CAN 状态反馈 | 17 | 部分实现 | 周期基本正确；状态帧大量字段占位；0x0A 停止码冲突；离合帧不适用 |
| LED 指示灯 | 11 | 未实现 | 灯帧全部硬编码绿灯 |
| SYS 综合联调 | 8 | 未实现 | 依赖一键、校准、故障闭环 |

## 4. 已经实现的业务

### 4.1 手动上升/下降与升降阀输出

- 键盘 → LiftControl → `valve_output` → 0x18FF1D60，按下开阀、松开关阀。
- 上下互锁：键盘消解 + 动作层再检查对向开关（[lift_actions.c](file:///d:/xl/vl_v.2.0.5/applications/lift/lift_actions.c#L34-L91)）。
- 对应 TC-MAN-005/006/007、TC-PRI-001 的举升部分。

### 4.2 举升角度采集与限位

- PA7 → ADC2 CH3，8 次过采样，1:2 分压还原（[lift_adc.c](file:///d:/xl/vl_v.2.0.5/applications/lift/lift_adc.c#L93-L126)）。
- 零点默认 2203mV，36.4mV/°（[lift_sensor_config.c](file:///d:/xl/vl_v.2.0.5/applications/lift/lift_sensor_config.c#L44-L64)）。
- 限位 +43°/-30°，容差 ±2°（[lift_angle.c](file:///d:/xl/vl_v.2.0.5/applications/lift/lift_angle.c#L29-L47)）。
- 50ms 限位检查（[lift_actions.c](file:///d:/xl/vl_v.2.0.5/applications/lift/lift_actions.c#L176-L202)）。
- 对应 TC-ANG-001~006 的换算部分、TC-MDL-009。

### 4.3 回转限位常量与手动方向拦截

- 左限位 -100°（电子限位 -101°），右限位 +215°（+216°），零位 ±0.5°，容差 ±2°（[swing_angle.c](file:///d:/xl/vl_v.2.0.5/applications/swing/swing_angle.c#L141-L199)）。
- `forbidden_dirs` 在 50ms tick 更新，手动进入 LEFT/RIGHT_RUNNING 时会拦截（[swing_actions.c](file:///d:/xl/vl_v.2.0.5/applications/swing/swing_actions.c#L143-L202)、[swing_actions.c](file:///d:/xl/vl_v.2.0.5/applications/swing/swing_actions.c#L234-L293)）。
- 对应 TC-ANG-007/008 的判定层（前提是角度真实）。

### 4.4 手动同轴互锁

- 同帧双按 → 两路都不输出。
- 双按变单按 → 剩下方向立即生效。
- 前后帧反向 ≤300ms → 冲突；>300ms 视为正常换向。
- 对应 TC-MAN-003/007、TC-PRI-001。

### 4.5 阀故障接收与上报

- 0x18FF0E63 → 故障码/通道反馈 → `g_solenoid`、LiftControl 故障状态（[ut_can_handlers.c](file:///d:/xl/vl_v.2.0.5/applications/CAN/ut_can_handlers.c#L104-L141)）。
- 0x18FF11D1 Byte2 上报 up/down 阀故障（[status_tx.c](file:///d:/xl/vl_v.2.0.5/applications/CAN/status_tx.c#L101-L104)）。
- 对应 TC-FLT-008~011 的“故障位读取”部分、TC-COM-011 的 Byte1 部分。

### 4.6 启车判据、ACC 门禁与启车重按

- 转速 >400rpm 或电压 >13.0V，各自独立计时 500ms（[vehicle_control.c](file:///d:/xl/vl_v.2.0.5/applications/vehicle/vehicle_control.c#L221-L249)）。
- STARTED 只由钥匙下电清除（[vehicle_trans_table.c](file:///d:/xl/vl_v.2.0.5/applications/vehicle/vehicle_trans_table.c#L58-L79)）。
- ACC 下电确认后拦动作开始（[app_main.c](file:///d:/xl/vl_v.2.0.5/applications/app_main.c#L94-L119)）。
- 进入 STARTED 时 `kb_request_rebaseline()`，按住不放的键必须松开重按（[vehicle_actions.c](file:///d:/xl/vl_v.2.0.5/applications/vehicle/vehicle_actions.c#L71-L91)）。
- 对应 TC-PWR-002~010 的大部分。

### 4.7 机型设置

- 0x18FF7F18 收到即覆盖、值去重、写 Flash 后回读核对（[ut_can_handlers.c](file:///d:/xl/vl_v.2.0.5/applications/CAN/ut_can_handlers.c#L158-L219)）。
- 0x18FF11D1 Byte3 上报设置状态与机型代码。
- 对应 TC-MDL-002/003/005/006/007/008；11 齿见 7.2。

### 4.8 发动机转速解析

- 0x0CF00400 Byte3~4，0.125rpm/bit，`raw >> 3`（[protocol_defs.h](file:///d:/xl/vl_v.2.0.5/applications/CAN/protocol_defs.h#L267-L290)、[ut_can_handlers.c](file:///d:/xl/vl_v.2.0.5/applications/CAN/ut_can_handlers.c#L235-L272)）。
- 100ms 超时归零。对应 TC-COM-016 的解析部分。

### 4.9 CAN 周期发送框架

- 0x18FF11D1/0x18FFA4F0 100ms，0x18FF1D60 200ms，模块开关默认全开（[can_tx_cfg.h](file:///d:/xl/vl_v.2.0.5/applications/CAN/can_tx_cfg.h#L49-L69)）。
- 对应 TC-COM-001/010 的周期部分。

## 5. 部分实现 / 断链项

### 5.1 P0：回转电机驱动没有接到业务状态机

- `motor_config.c` 的 `drv_ops/fb_ops/ctrl_ops` 全为 NULL（[motor_config.c](file:///d:/xl/vl_v.2.0.5/applications/motor/motor_config.c#L52-L92)）。
- `motor_start()` 不会写 PWM，`motor_stop()` 不会停 PWM（[motor.c](file:///d:/xl/vl_v.2.0.5/applications/motor/motor.c#L110-L133)）。
- `Foc_Mode_PwmOwned()` 恒 1，`motor_update()` 被门控跳过（[bg_modules.c](file:///d:/xl/vl_v.2.0.5/applications/bg_modules.c#L63-L70)、[foc_mode.c](file:///d:/xl/vl_v.2.0.5/applications/motor/foc/foc_mode.c#L390-L397)）。

现象：手动左/右只解锁/锁止刹车，电机不转。TC-MAN-001/002/004、TC-PWR-002 的左/右、TC-ONE-* 全部阻断。

### 5.2 P0：回转角度反馈恒为 0

- `swing_init()` 绑定 `motor->current_position`（[swing_init.c](file:///d:/xl/vl_v.2.0.5/applications/swing/swing_init.c#L20-L44)）。
- 该字段唯一写入点在 `motor_fb_abs_encoder.c` 已被整段注释，Hall 的 `get_position` 也为 NULL（[motor_fb_abs_encoder.c](file:///d:/xl/vl_v.2.0.5/applications/motor/fb/motor_fb_abs_encoder.c#L156-L199)）。
- FOC 的 ABZ `g_enc_count` 没有接到 `swing_angle`（[hw_encoder.h](file:///d:/xl/vl_v.2.0.5/applications/motor/foc/hw_encoder.h)）。

结果：零位恒成立、左右限位永不触发、一键 `SWING_NEAR` 目标非 0 时永不满足、状态帧角度无法填。TC-ANG-007/008/011/012、TC-MAN-004、TC-ONE-*、TC-COM-008 全部受阻。

### 5.3 P0：一键序列没有驱动源

- ONKEY 事件没有交给 seq_control。
- `seq_control_update()` 零调用，序列永远停在第一步。
- `seq_control_update_onekey()` 的语义也与用例不符：当前任何一键上升沿都会 abort 当前序列（[seq_control.c](file:///d:/xl/vl_v.2.0.5/applications/sequence/seq_control.c#L227-L262)）；用例要求：
  - 同一键重复按 → 忽略，不重启（TC-ONE-012、TC-PRI-006）。
  - 其他一键 → 立即中断并执行新动作（TC-ONE-013、TC-PRI-004）。

### 5.4 P0：0x18FF11D1 大量字段是占位

`status_tx.c` 中 `TODO(N-1)`：

| 字段 | 当前值 | 用例要求 |
| --- | --- | --- |
| power_voltage_sta | 恒正常 | 12V→00、10V→01、15V→10（TC-COM-002） |
| comm_sta | 恒 0 | CAN 静默 300ms → 1（TC-FLT-015） |
| work_mode | 恒 000 | 手动 001、一键展开 010、一键回位 011（TC-COM-003、TC-ONE-017） |
| encoder_sta | 恒 0 | 编码器故障 → 1（TC-FLT-006/007） |
| motor_sta | 恒 000 | 左转 001、右转 010、停止 000、堵转 100（TC-COM-004） |
| lift_sensor_sta | 恒 0 | 传感器故障 → 1（TC-FLT-001/003） |
| lift_sta | 恒 000 | 上升 001、下降 010、停止 000（TC-COM-005） |
| swing_angle_raw | 恒零位 | 偏移 -300°，1°/bit（TC-COM-008） |
| lift_angle_raw | 恒零位 | 偏移 -90°，1°/bit（TC-COM-009） |

证据：[status_tx.c](file:///d:/xl/vl_v.2.0.5/applications/CAN/status_tx.c#L55-L133)。

### 5.5 P1：升降阀停止码与用例冲突（O-03）

- 代码：停止时上升/下降均为 00，Byte3=0x00（[valve_tx.c](file:///d:/xl/vl_v.2.0.5/applications/lift/valve_tx.c#L36-L43)）。
- xl.xlsx `02_信号定义` Byte3 备注：“0x0A 为停止（O-03）”；TC-COM-010 也要求发送 0x03/0x0A/0x0C。
- 结果：上升 0x03、下降 0x0C 一致；停止码可能是 0x00 或 0x0A，需按 O-03 结论确认。

### 5.6 P1：限位后 5s 保持被禁用

- Q29 裁定把举升到限位后的 5s 保持注释掉，直接回 IDLE 关阀（[lift_trans_table.c](file:///d:/xl/vl_v.2.0.5/applications/lift/lift_trans_table.c#L62-L79)、[lift_actions.c](file:///d:/xl/vl_v.2.0.5/applications/lift/lift_actions.c#L94-L116)）。
- 用例 TC-MAN-008、TC-ANG-009/010 明确要求“到限位后阀继续输出 5s（±0.5s）再失电”。

### 5.7 P1：手动过零停车被禁用

- `need_zero_stop` 默认 0，注释称用户裁定“手动模式跳过零位”（[swing_angle.h](file:///d:/xl/vl_v.2.0.5/applications/swing/swing_angle.h#L68-L81)）。
- 用例 TC-MAN-004 明确要求：从 -5° 右转到 0° 自动停止，保持按住不继续，松开重按才继续。
- 当前实现与用例相反。

### 5.8 P1：传感器故障行为与阈值不符合用例

- 代码：>4700mV 或 <300mV 立即故障（[lift_sensor.c](file:///d:/xl/vl_v.2.0.5/applications/lift/lift_sensor.c#L170-L185)）。
- 用例：4800mV 持续 2.5s → 2s 后故障；4400mV 2.5s → 2s 后恢复；250mV 2.5s → 故障；520mV 2.5s → 恢复（TC-FLT-001~004）。
- 代码无 2s 确认/恢复延时。
- 故障后 LiftControl 进入 `P_STATE_FAULT_SENSOR`，手动上升/下降被自转移拦住（[lift_trans_table.c](file:///d:/xl/vl_v.2.0.5/applications/lift/lift_trans_table.c#L120-L123)）；用例 TC-ANG-013 要求“一键不启动，仅保留允许的手动控制”。

### 5.9 P1：下电不停止正在执行的动作

- app_main 收到 `SYS_EVT_ACC_OFF` 只清序列副本并刷新灯帧（[app_main.c](file:///d:/xl/vl_v.2.0.5/applications/app_main.c#L217-L222)）。
- 没有对 LiftControl 发停止、没有对 SwingControl 发停止，也没有关阀。
- 用例 TC-PWR-011 要求动作过程中钥匙下电立即停止输出。这是安全项。

### 5.10 P1：一键“回位已在零位”会先上升

- 代码 home 序列固定从“升到 +25”开始（[seq_config.c](file:///d:/xl/vl_v.2.0.5/applications/sequence/seq_config.c#L85-L121)）。

### 5.11 P1：回位 2s 保持是空动作

### 5.14 P2：面板类型未使用

## 7. 用例自身需要确认的问题

### 7.1 旧用例与 xl.xlsx 的冲突

旧 `水稻机卸粮系统测试用例.xlsx` 的 VG02-005 多处要求“同时上升+回转”；xl.xlsx 的 ONE 模块明确是：

    先升到 +25° → 开始转 → 到目标角停转 → 继续升到 +34° 关阀

代码 `seq_config.c` 的顺序与 xl.xlsx 一致。**旧用例的“同时动作”描述不再作为缺口依据**。

### 7.2 11 齿机型编码（O-01）

- 协议定义：0=13 齿、1=14 齿、2=11 齿。
- TC-MDL-004 预期：Byte3 bit1~2 = 1（11 齿），同时备注“CAN 协议中查询反馈没有 11 齿的编码”。
- 代码：`TEETH_11 → teeth_code = 2`。
- 三者不一致，需按 O-01 结论统一。

### 7.3 18FF1D60 停止码（O-03）

- 用例：上升 0x03、停止 0x0A、下降 0x0C（TC-COM-010）。
- 协议备注：“00/01 不控制、10 无效、11 有效”，又说“0x0A 为停止”。
- 代码：停止 0x00。
- 需要确认 RGV 实际接受的停止码，否则 TC-COM-010 会判不通过。

### 7.4 升降角 Byte7 的符号解释

- 协议：有符号整数，偏移 -90°，1°/bit。
- 代码：`uint8_t lift_angle_raw`，默认 90。
- 0° → 90，-30° → 60，+43° → 133。若 HMI 按 int8 解码，+43° 会变成 -123 → -213°，需要确认 HMI 的解析方式。

### 7.5 TC-ANG-006 的数值自相矛盾

- 用例：“注入低于零点约 456mV，输出约 -30°”。
- 按 36.4mV/° 计算，456mV 只有 -12.5°；-30° 应约 -1092mV。
- 需要确认是注入 1747mV（-12.5°）还是 1111mV（-30°）。

### 7.6 传感器故障阈值与延时

用例给的是 4800/4400/250/520mV + 2s 确认/恢复；代码是 4700/300mV 立即。需要确认最终阈值与“2s”是否适用于本控制器（有些项目把 2s 放在 HMI 侧）。

### 7.7 CAN 通信故障门限

用例 TC-FLT-015 写“无报文 300ms（暂定）”；代码 `can_is_bus_silent` 用于整车故障，门限 500ms，且整车 FAULT 还要连续 2s；状态帧 `comm_sta` 未填。需要确认 300ms 是否最终值、以及“任一帧”还是“特定报文”。

### 7.8 LED 规则中的未定义项

- TC-LED-005 备注“其实不知道机构灯是啥”。
- TC-LED-009 对过欠压“红快闪”与“过压/低压保护红常亮”自相矛盾，频率未定。
- TC-LED-010 “开短路灯色待确认”。
- 这些需要客户给出最终灯效表，否则无法判定。

### 7.9 8 键面板行为

TC-CAL-012/TC-LED-011 要求 8 键面板“4 键自身灯上电常亮、下方状态灯不亮”。当前代码完全不区分面板类型，`remote_type` 被忽略。

### 7.10 启车台架条件

TC-PWR-003/004 需要 450rpm 或 13.5V 才能启车。台架若只有 12V 且不注入 0x0CF00400，所有一键类用例都无法进入前置条件。

## 11. 分析思路与判定依据

本节记录上面结论是怎么得出来的，便于后续复查、补充或推翻。

### 11.1 分析目标与边界

目标不是“逐条执行 146 条用例”，而是回答三个问题：

1. 从代码看，这条用例的端到端链路是否存在。
2. 如果存在，断在哪一环；如果不存在，是缺模块还是被门控。
3. 用例与协议本身是否有冲突或未定义项。

边界：

- 只做静态代码追踪，不做台架实测。
- `xl.xlsx` 是主依据；旧 `水稻机卸粮系统测试用例.xlsx` 只用于交叉检查，冲突时以 `xl.xlsx` 为准。
- 角色边界按 `xl.xlsx 00_说明与约定`：本工程只负责 UTMotVCU，不替 CPB/HMI/RGV/离合 VCU 实现它们的职责。

### 11.2 分析步骤

实际按以下顺序做：

1. **先读需求结构**：读 `xl.xlsx` 的 17 个工作表，先建立“10 条报文 + 12 个用例模块 + 146 条用例”的索引，再看 `02_信号定义` 确认每个 Byte/bit 的归属。
2. **再建运行模型**：从 `main()` 进 `boot_table.c`，确认哪些模块被初始化；再进 `app_main.c`，确认 50ms tick、事件路由、两道门禁和线程模型。
3. **按模块追链路**：对 PWR/MDL/ANG/MAN/ONE/CAL/CLT/PRI/FLT/COM/LED/SYS 逐模块，从“CAN 输入 → 事件 → 状态机 → 动作 → 输出 → 状态反馈”走一遍。
4. **找断点**：每个链路必须找到“最后一处有效代码”和“第一处缺失代码”，避免只凭某个函数存在就判“已实现”。
5. **查占位**：全局搜 `TODO`、`恒 0`、`return 0`、`NULL`、`hardcode`、`注释`，识别“代码在但值是假的”情况。
6. **查调用者**：对关键更新函数（`seq_control_update`、`motor_update`、`lift_angle_update`、`swing_angle_update`）确认是否真的有人调用。
7. **对照新旧用例**：把旧 VG02 文档与新 `xl.xlsx` 的差异列出来，避免拿过期需求当缺口。

### 11.3 判定口径

| 判定 | 含义 |
| --- | --- |
| 已实现 | 从输入到输出/反馈的代码链路完整，且无已知占位、无被全局门控跳过 |
| 部分实现 | 至少一个关键环节缺失、占位、被门控，或只在某个子场景成立 |
| 未实现 | 没有业务对象、没有事件消费者、没有输出，或整条链路不存在 |
| 不适用 | 按角色边界属于 CPB/HMI/RGV/离合 VCU 的职责 |
| 待确认 | 用例或协议自相矛盾、开口项未定，不能直接判通过/不通过 |

“函数存在”不算已实现。比如 `motor_start()` 存在，但它的 `ctrl_ops` 为 NULL，实际不写 PWM，就判部分/断链。

### 11.4 链路追踪模型

每条用例都按同一条链检查：

    CAN 输入 / 内部事件
      → 门禁（ACC / 启车 / 模式能力 / 故障降级）
      → 描述表路由
      → 控制对象状态机
      → 动作函数
      → 硬件输出（PWM / 阀 / CAN 帧）
      → 状态反馈（0x18FF11D1 / 0x18FFA4F0）

只要有一环是“代码存在但实际不生效”，就继续往下找它为什么失效，直到找到根因或下一个缺失点。

### 11.5 三个典型断链的定位过程

#### 11.5.1 手动左/右为什么“刹车动、电机不动”

追踪顺序：

1. 0x18FF8380 Byte1 left/right → `keyboard_scan.c` 生成 `KB_LEFT/KB_RIGHT`。
2. `keyboard_sm.c` 边沿检测 → `post_event(SWING_EVT_LEFT_DOWN/RIGHT_DOWN)`。
3. `app_main.c` 门 1/门 2 放行（手动只要求 ACC）→ 描述表路由到 SwingControl。
4. `swing_trans_table.c` IDLE → UNLOCKING → `swing_act_enter_unlocking()` 调 `hw_brake_unlock()`。
5. 50ms tick 看到刹车已解锁 → `SWING_EVT_BRAKE_UNLOCKED_LEFT/RIGHT` → LEFT/RIGHT_RUNNING。
6. `swing_act_enter_left_running()` → `swing_motor_start()` → `motor_start(&g_swing_motor)`。
7. `motor_start()` 只检查 `motor->ctrl_ops->set_target`；`motor_config.c` 里 `ctrl_ops = NULL`，函数直接返回。
8. 同时 `bg_modules.c` 的 `motor_update()` 被 `Foc_Mode_PwmOwned()` 恒 1 跳过；FOC 又没有接收业务给定。

结论：断点在“业务状态机 → 电机对象”这一层，不在键盘，也不在刹车。判部分实现。

#### 11.5.2 回转角度为什么恒 0

追踪顺序：

1. `swing_init()` 把 `swing_encoder_getter` 绑定为 `motor->current_position`。
2. `swing_angle_update()` 每 50ms 调 `get_encoder()` 得到这个值。
3. 全局搜索 `current_position` 的写入点：唯一一处 `motor_fb_abs_encoder.c` 已被整段注释；Hall 的 `get_position` 也是 NULL。
4. FOC 的 `g_enc_count` 只在 FOC/VOFA/标定内部使用，没有写到 `motor->current_position`，也没有被 `swing_angle` 读取。
5. `abs_angle_solve()` 只在 msh 命令和 `motor_angle` 里调用；`BSP_USING_ABS_ENCODER=1` 时 SPI 编码器初始化也被跳过。

结论：业务拿到的角度不是“滤波不好”，而是数据源恒 0。判断链。

#### 11.5.3 一键为什么完全没反应

追踪顺序：

1. `keyboard_sm.c` 只投 `SWING_EVT_ONKEY_*`。
2. `obj_desc.c` 把 0x2000 区间路由到 SwingControl。
3. `swing_trans_table.c` 没有任何 ONKEY 行 → 状态机查表失败，事件被静默丢弃。
4. `keyboard_sm.c` 对 `seq_control_update_onekey()` 只传 `0,0,0`，不会触发序列。
5. `seq_control_update()` 没有调用者；`app_main.c` 里那行被注释。
6. 所以即使手动调用 `seq_engine_start()`，也没有周期推进。

结论：一键不是“动作参数不对”，而是从按键到序列引擎的第一跳就断了。判未实现。

## 12. 存储与电角度标定方案（2026-11-19）

本节只记录方案对业务的影响，技术细节见 `移植过程.md` 的 10.15 节。存储主体已落地；SPI 绝对编码器仍未实现。

### 12.1 当前状态

- 没有持久化的“绝对编码器—电角度”偏移；`g_enc_elec_offset` / `g_enc_elec_dir` 只存在 RAM（[hw_encoder.c](file:///d:/xl/vl_v.2.0.5/applications/motor/foc/hw_encoder.c#L70-L71)）。
- 当前构建只调通了 ABZ；SPI 绝对编码器尚未实现，上电后需要人工先做 mode 3。
- 没有 bootloader/OTA 实现；`ota_shared` 只是状态记录。

### 12.2 目标行为

1. 首次烧录后：人工做一次两点式强拖校准（mode 3），记录绝对编码器在电角度 0 时的原始值。
2. SPI 绝对编码器接入后：后续上电读快区记录 + 绝对编码器，直接算出电角度，再用 ABZ 做运行期快速更新，不再强拖。
3. 校准后立即保存快区：两点式校准结束、电机停止的安全窗口读取偏移并与 Flash 比较；差值超出容差（原始计数 ±4 counts）才写入，容差内不重存。运行中不做动作前校准。
4. mode 7 不启用：它不是一点式校准，本次不为它做存储或时序适配。
5. 收到转动指令后：固定等待 501ms 再允许动作，无论是否发生存储，保证体感一致；存储/校准不得在 FOC 运行中或 20kHz ISR 中执行。
6. 欠压：连续 30ms 低于阈值判定；欠压不作为角度存储触发，角度在每次校准后已保存。

### 12.3 存储布局摘要

| 区 | 扇区 | 用途 |
|---|---:|---|
| MOTION 慢 | 56 | 电流零点、极对数、PWM、过流/堵转、测速 |
| ANGLE/MECH 慢 | 57 | mech 选择子、active 行、编码器零点、校准标志、方向 |
| SYSTEM 慢 | 58 | 整车/ACC/看门狗/CAN/mode/举升 |
| FAST 角度 | 59~61 | 绝对编码器—电角度标定常数，3 扇区轮转 |
| 预留 | 62 | 用户其他用途 |
| DEVICE 慢 | 63 | SN、型号、版本、生产日期 |

- 慢区不再限制 10000 次擦除；快区每个扇区 10000 次擦除寿命：写满后先原地擦除重用，擦除次数到 10000 后，下一次写满才换扇（61→60→59→61）。
- `t_mech_set` 会持久化 active 行的 13 个字段（32B）+ 选择子/active_idx/count；只存 5 个字段不够，非 active 行不持久化。上电是否按 cfg 重选行看记录里的三个选择子，不看整行，避免 `t_mech_set` 的手工修改被候选表覆盖。
- 擦写是否关中断由宏 `PARAM_EFM_CRITICAL_DISABLE_IRQ` 控制，默认开启（关中断），与 FA04A 参考工程一致。
- 参数区写入/擦除前会检查应用镜像结束地址，低于 `code_end` 的地址直接拒绝，防止误擦代码。

### 12.4 怎么看存储是否正常

完整指令与调试器观察点见 [测试存储msh.md](file:///d:/xl/vl_v.2.0.5/测试存储msh.md)。

1. 上电自检末尾自动打印一次（启动步骤 `param_dump`）：
   - `storage status`：每组记录的扇区、单条大小、当前扇区 `left=剩余/总槽位`、擦除次数、`seq`、`src`；
     `src=FLASH` 表示记录来自 Flash 且 CRC 校验通过；`src=DEFAULT` 表示该组仍是本次上电写入的默认记录（尚未真实保存）。首次烧录时 motion/system 会在 `sys_config_init` 中立即落盘，同一轮启动内即变为 `FLASH`；`angle_mech`/`fast` 在没有任何真实标定前保持 `DEFAULT`。
   - `current values`：`motion/system` 逐项打印 `0xID 名称 = 值`；`angle_mech/device/fast` 按字段打印。
2. 运行时用 MSH：
   - `t_param`：存储状态 + 全部当前值；
   - `t_param info`：只看扇区余量/擦除次数/seq；
   - `t_param values`：只看当前值；
   - `t_param set <id|name> <val> [save]`：改 RAM，带 `save` 立即落盘（范围校验与 `t_cfg` 相同）；
   - `t_param save [all|cfg|am|dev|fast]`：按业务打包手动落盘；默认 all 只写 CFG/AM/DEV，`fast` 单独触发快区写入；
   - `t_param write <motion|system|angle_mech|device|fast> [count]`：对某区精确写入 `count` 次（默认 1），只消耗该区槽位；
   - `t_param erasecnt <group> <n>`：把该组当前扇区擦除次数设为 `n`（只改 RAM）；fast 设 `>=10000` 后，下次**写满**才换扇；
   - `t_param erase [all|slow|fast] confirm`：一键擦除快/慢区，并把当前 RAM 值重新写回（格式化语义，保留 SN/机械行/配置）；电机运行中拒绝；
   - `t_param fill <motion|system|angle_mech|device|fast> [leave]`：反复写入当前值，直到当前扇区只剩 `leave` 个槽位（默认 2）。
   - WORK 模式下申请 `PARAM_WRITE` 的命令（`t_param`、`t_mech_set`、`t_cfg` 等）在 `focmode 0/1` 时临时放行（`sys_caps.c` 的 `SYS_CAP_TEMP_ALLOW_PARAM_WRITE`，正式版改 0）；其它 FOC 模式仍拒绝。
3. 快区写满/换扇验证：
   - 原地擦除：`t_param fill fast 0` 写满后 `t_param write fast 1`，`cur` 不变、`erase` 加 1、`left=185/186`；
   - 寿命换扇：先 `t_param erasecnt fast 10000`，再 `fill fast 0`、`write fast 1`，`cur` 才切到下一扇区（61→60→59→61），新扇区 `erase=1`；
   - `erasecnt` 只在 RAM 生效，不写 Flash。
4. 判定标准：
   - 有有效记录时 `src=FLASH`，且 `seq`、`wr` 随保存递增；
   - 保存后 `left` 减少 1；慢区写满后原地擦除，`erase` +1、`left` 回到满值；
   - 快区写满后先原地擦除（`cur` 不变、`erase` +1）；擦除次数到 10000 后再写满才换扇；
   - 快区三块各自有 `left`，当前块标 `*cur`，其余块换扇时会先擦除，按满容量显示。
5. 所有打印只用整型/ASCII，不含中文和浮点（RTT 控制台限制）。

### 12.5 与当前业务断链的关系

- 该方案只解决“电角度偏移的持久化与上电恢复”，不解决 5.1（回转电机驱动未接入）、5.2（回转角度恒 0）、5.3（一键无驱动源）。
- 校准状态机（CAL 全模块、按键双击/长按/灯效/次数限制）仍未实现；本方案只提供存储和电角度接口。

### 12.6 待确认

已裁定：mode 7 不启用；快区容差为原始计数 ±4 counts；`t_mech_set` 只持久化 active 行；擦写默认关中断（与 FA04A 一致）。

## 13. 卸粮筒绝对角与上电校准方案（2026-11-20 确认稿 v3，待实现）

> 本节记录 P0-1「绝对角来源」的暂定决策，**尚未实现**。冲突时以本节为准，取代 §4.6/§12 中"必须先决策"的表述。

### 13.1 硬件与现状约束

| 项 | 现状 |
| --- | --- |
| 编码器 | 现场只有 **ABZ 增量编码器**（TMRA1 正交计数，4096 CPR，10 对极）；SPI 绝对编码器（KTH7812）代码**保留但不启用**（`BSP_USING_ABS_ENCODER = 1`） |
| 计数原点 | `hw_encoder_init()` 每次上电 `TMRA_SetCountValue(CM_TMRA_1, 0)` + `s_count = 0`（`hw_encoder.c:167-183`）→ **计数零点随上电时的转子位置变化** |
| 机械 | **机械自锁**结构：掉电与重上电前后转子位置不变，不会被外力转动 |
| 减速比 | **1080**（电机 → 卸粮筒，`216 × 65/13`） |
| 筒水平角 | `tube_deg = count / 4096 / 1080 × 360`；电机 1 个电周期 = 筒 0.0333° |

### 13.2 关键认知：offset 是「计数域」量，不能直接跨上电复用

`g_enc_elec_offset` 由 mode 3 的 ALPHA 段算出：`offset = count % CPR`（`encoder_calib.c:763-767`）。它只对**本次上电的计数原点**成立；上电清零后原点变了，同一个 offset 数值对应的是另一个物理角度。

因此快区里的 offset 存档，真正作用是：

1. 保存 `elec_dir`（电角度方向）与 `pole_pairs` 等**与原点无关的常量**——一点式对齐给不出 dir，必须有存档；
2. 作为上电后一点式对齐结果的**比较基线**（判断是否要重写）。

> 结论：**电角度**靠"上电 α 一点式对齐"重建，不靠 offset 存档直接恢复；**筒绝对角**则是另一个问题（见 13.4 第 1 条）。

### 13.3 方案（2026-11-20 确认版 v3，待实现）

1. **两点式 mode 3**：ZERO→BETA 90°→ALPHA 0°，得到 `offset` 与 `dir` 写入快区；**完成后把筒角置 0**，并把"筒角=0 + 当前指纹"一起写快区快照。
2. **一点式对齐 = 独立的一次性流程**（不是向量环内部的一步）：施加 α 对齐矢量（默认 1.3 V）→ 保持 200 ms → 读编码器 count → 计算 offset → 结束并退回 `mode 0`（或 `mode 1`）。
3. **触发条件**：只在**「停止态 → 进入向量环（电流/速度/位置）」**时做一次；序列内部步骤（升→转→升）与环间切换**不重复**做。
4. **500 ms 门限**：从收到动作指令计起，窗口内完成"解锁抱闸 + 一点式对齐（约 200~250 ms）"，到 500 ms 再切向量环。该 500 ms 与既有需求 **P2-4「收到转动指令后 501 ms 门限」合并实现**。
5. **指纹比对**：对齐结果与快区指纹比较（counts 域），`|Δ| ≤ 5 counts` → 不写；`> 5 counts` → 写新 offset。±5 counts ≈ ±4.4° 电角度。
6. **筒角**：一点式对齐**不影响**筒角；两点式把筒角置 0；跨上电由快区快照恢复，指纹不一致则作废、要求重新两点式。
7. **减速比 1080**（`216 × 65/13`）：`tube_deg = count / 4096 / 1080 × 360`；电机 1 个电周期 = 筒 **0.0333°**。
8. **失败处理**：**一点式对齐不判失败**——它本身没有"前后 count 变化"可比，流程跑完即有效。**两点式 mode 3 已有保护**：BETA 与 ALPHA 之间的 `moved == 0` 判无效（`encoder_calib.c:868-876`，打印 "ABZ not connected or rotor not moved"）。
9. **存档触发（v3 确认）**：**只有欠压触发存档**——母线电压低于 **11 V** 连续 **30 ms**；上电后有 **200 ms 消隐期**，消隐结束才开始测电压。**ACC（钥匙）下电只做急停，不存档**。
10. **欠压动作顺序**：欠压事件 → **急停（回转 + 升降阀 + 一键序列全停）** → **等编码器 count 稳定 20 ms** → 关中断 → 写一组快区数据（不去重，每次欠压必写）。
11. **欠压恢复**：电压回升到 **12 V**（迟滞）后恢复判定；恢复时间窗待定（建议 500 ms 连续满足）。不复用 vehicle 的 FAULT 态（后者只能靠 ACC 下电清除，打火跌落会导致整机锁死）。
12. **掉电保持时间**：初测约 **250 ms**，够"30 ms 确认 + 急停 + 20 ms 稳定 + 编程（约 1 ms）"。
10. **参数区变更**：当前为设计阶段、每次烧录整片擦除，因此快区字段可自由增删，**不需要兼容旧记录**；但布局变化仍需换魔数（避免旧固件记录被误读）。

### 13.5 指纹校验的固有限制（必须知晓）

`offset = count % CPR`，只反映**一个电机转内的相位**。在 1080:1 + 4096 CPR 下：

- 筒转 **1/3°** = 电机 **1 整圈** = 4096 counts → **指纹完全不变**；
- 因此任何"整数倍 1/3°"的筒位移，指纹都发现不了；
- ±5 counts 阈值本身只相当于筒 **0.0004°**，远小于盲区，所以阈值不是问题，**盲区才是**。

结论：

1. 指纹只能作为**弱校验**，用于发现"非整数倍 1/3°"的外部位移；
2. 真正的安全性依赖**机械自锁**（掉电后没人能转筒）；
3. 现场规程要按"指纹通过 ≠ 位置绝对没变"来写。若将来需要更强校验，只能恢复绝对编码器或加独立基准开关。

### 13.6 欠压状态机与快区预擦除（实现建议）

**A. 欠压状态机（新增，不复用 vehicle FAULT）**

现状：`sys_voltage` 只测不判；vehicle 有 `FAULT` 态，但**只能靠 ACC 下电或 force reset 清除**（`vehicle_trans_table.c:77-78`），若把欠压接进去，打火跌压会导致整机锁死，不合适。

建议独立状态机：

```
POWER_NORMAL
  --(v < 11.0 V 连续 30 ms，且已过 200 ms 上电消隐)--> POWER_UV

POWER_UV
  动作：急停（回转 + 升降阀 + 一键序列）→ 等 count 稳定 20 ms
        → 关中断 → 写一组快区数据 → 上报 power_voltage_sta = 欠压
  门禁：msh 仍然可用；**FOC 转动控制相关操作被拒绝**——
        Foc_Run_SetMode 拒绝 IF/CURRENT/SPEED/POSITION（置失败 + 打印）；
        Foc_Proc_Start 拒绝 3/5/6/7 标定与一点式对齐（都需要转矩）；
        仅放行 IDLE(0)、只读诊断（fstat/t_abz/t_iadc/t_param/t_cantx 等）
  说明：拒绝发生在 FOC 层（`Foc_Run_SetMode`/`Foc_Proc_Start` 入口），
        业务层与 msh 都会因此被拦住，不需要每处调用者自己判断
  --(v > 12.0 V 连续 500 ms)--> POWER_NORMAL（自动恢复，不要求 ACC 重上电）
```

- 上报：`status_tx.c` 的 `power_voltage_sta`（当前是占位，恒填正常）→ 0=正常、1=欠压、（2=过压预留）。
- 诊断：欠压次数记入慢区/设备区，便于现场判断电源问题。
- 不把欠压位加进 `vehicle_fault_word`：加了会触发 vehicle 的 2 s FAULT 锁存。

**参数配置（放 `sys_config` 的 SYSTEM 慢区）**

| 参数 | 建议 ID | 默认（宏） | 范围 |
| --- | --- | --- | --- |
| 欠压判定门限 | `CFG_ID_UV_ENTER_MV` | `CFG_DEF_UV_ENTER_MV = 11000` | 8000~14000 mV |
| 恢复门限（迟滞） | `CFG_ID_UV_RECOVER_MV` | `CFG_DEF_UV_RECOVER_MV = 12000` | 9000~16000 mV |
| 欠压确认时间 | `CFG_ID_UV_CONFIRM_MS` | `CFG_DEF_UV_CONFIRM_MS = 30` | 10~500 ms |
| 恢复确认时间 | `CFG_ID_UV_RECOVER_MS` | `CFG_DEF_UV_RECOVER_MS = 500` | 100~5000 ms |
| 上电消隐期 | `CFG_ID_UV_BLANK_MS` | `CFG_DEF_UV_BLANK_MS = 200` | 100~2000 ms |

> **关于"宏定义可调"的现状说明**：现有 `sys_config` 的默认值不是宏，而是**直接写在 `s_cfg_def[]` 表里的字面量**（如 `{ CFG_ID_ACC_ENTER_MS, "acc_enter_ms", CFG_T_U16, CFG_F_REQ_RESTART, 500, 100, 5000, "ms" }`）。机制本身是"上电先加载默认值 → 再逐项合并 Flash"，所以**首次烧录/全片擦除时用表里的默认值，已落盘的设备继续用 Flash 值**，改默认值不影响现场设备。
> 本次按你的要求改成宏：在 `sys_config.h` 定义 `CFG_DEF_UV_*`，表中 `def_val` 列引用宏。这样"改宏 → 重新烧录 → 生效"的语义不变，但更直观、便于统一调整。

**B. 快区预擦除（保证下电只编程）——按 FA04A 参考工程实现**

现状（`param_manager.c`）：
- `Param_Save()` 先调 `ensure_space()`：**只在本次写入前**检查当前扇区剩余空间；不够就**当场擦除**——慢区原地擦；快区若未到 10000 次擦除寿命也是原地擦，到了才换扇。
- 上电只 `param_store_boot_dump()` 打印状态，**不预判空间、不补擦**。

参考工程 `D:\FA04A_v.1.0.0\RTT_template1\Utils\param_manager.c:260-280` 的做法（**本次采用**）：

> 上电扫描加载完成后，若"剩余空间不足以再存一次"（即 `slots_left < 1`），**在满电的上电期就地擦除当前扇区**，把当前记录回写到扇区头（`erase_count + 1`、重算 CRC），写指针指向下一空位。
> 目的：把边界擦除从"掉电保存途中"挪到"上电安静期"；该条件与 `Param_Save` 溢出条件互补——预擦除未触发的上电，之后首次保存必然装得下，因此正常"一次掉电一存"工况下，掉电途中永远不会触发擦除。
> 兜底：擦除失败则保留原指针，下次保存走 `ensure_space()` 原地擦除分支。

本工程落地方式（3 扇区快区 + 10000 次寿命轮转）：

| 项 | 设计 |
| --- | --- |
| 触发条件 | 快区 `slots_left < 1`（**不是** <4，按参考工程） |
| 动作 | 等价于"立即再存一次"：`ensure_space()` 决定原地擦除或换扇 → 随后写入一条当前记录（seq+1、erase_count 更新、重算 CRC） |
| 调用时机 | **上电自检完成、业务启动前**（`param` 启动步骤末尾），仅快区 |
| 实现成本 | 无需新增 `param_manager` API：查快区状态后调 `param_store_save_now(PARAM_REQ_FAST)` 即可 |
| 慢区 | 不处理（单扇区写满只能原地擦）；欠压只写快区，不受影响 |
| 代价 | 上电时可能多一次擦除（数十 ms），但发生在满电期 |

**C. 欠压写快区路径（只编程，不擦除）**

固定顺序：急停 → 等 count 稳定 20 ms → 关中断 → `param_fast_save_now()`（更新 RAM + 同步写一条）→ 等电掉（或软复位）。
> 必须只写一条：`param_fast_save()` 会额外投异步请求，多写的记录会多占槽位，可能在下电瞬间触发扇区擦除。
若写入过程中断电导致记录损坏：CRC 校验会跳过坏记录、回退到上一条 → 下次上电指纹校验发现不一致 → 筒角作废（安全兜底）。

### 14.4 每批的 msh 交付标准（模板）

1. **只读观测**：一条命令打印该模块全部关键量，全 ASCII/整数，单行 ≤126 字符（RTT 限制）。
2. **注入/强制**：能绕过外部输入直接触发，粒度与 `t_sim` 一致，便于分离"输入端"与"逻辑端"。
3. **脚本登记**：写入 `input_sim.c` 的 `s_seqs[]`，命名 `m<编号>`，
   每步先打印 `[seq] (i/n) <命令>` 再执行；需电机的脚本在描述里标 `[MOTOR]`。
4. **判据回写**：在 `测试用例_业务层.md` 增加对应 M 编号与逐行预期，
   不允许只写"通过/不通过"。
5. **回归**：每批完成后跑上一批脚本 + 既有 `m3/m4/m6/m7/m9/m10`；
   改动涉及状态帧的还要跑 `m19`。
6. **降级开关**：每批新逻辑都留一个 `sys_config` 开关或宏，
   现场可退回旧行为（例如 `swing_zero_stop`、`lift_hold_ms=0`、`can_fault_ms`）。

### 14.7 仲裁架构与 RT-Thread 组件分工（2026-11-21 讨论定稿）

> 本节记录 §14 各批次的**实现骨架**：仲裁层怎么放、每类输入配什么组件、
> 停止类事件如何不丢。模块清单与顺序仍以 §14.2 / §14.3 为准，本节只补充"怎么做"。

#### 14.7.1 决策摘要

| 项 | 结论 | 理由 |
| --- | --- | --- |
| 仲裁层位置 | **集中仲裁器 + 正交模块** | 模块状态数不爆炸；优先级只在一张表里维护；每批可单独回滚 |
| 仲裁器形态 | 纯函数，不 include 任何 RTOS 头 | 可在 host gcc 下单测；只被 `app_main` 单线程调用，内部无需加锁 |
| 接入方式 | **路由前过滤器**（先仲裁，再 `control_object_process`） | 不重写 swing/lift 跳转表，改动小、可回滚；跑稳后再把 owner 判定收进模块 |
| 事件总线 | 保持单一 `rt_mq` | 离散、有顺序、单消费者，语义最贴 |
| 丢事件策略 | **单队列 + 停止类不丢** | 队列满时停止语义仍生效，且优先于任何动作请求 |
| 周期判定 | 50 ms tick + 各 ctx 的 `*_tick` 字段 | 避免"每个延时一个 soft timer"导致 timer 数量爆炸与并发加锁 |
| 独立定时器 | 只保留 `sys_voltage` 10 ms、CAN 发送、VOFA | 这些需要独立时间基准，或与业务线程解耦 |

#### 14.7.2 现状与必须先修的问题

| 项 | 现状 | 影响 |
| --- | --- | --- |
| 事件队列 | `ipc_center.c:23`：`rt_mq_create("evt_mq", 4, 32, RT_IPC_FLAG_PRIO)` | 深 32；`RT_IPC_FLAG_PRIO` 只决定"多线程等待时的唤醒顺序"，**不代表消息本身有优先级** |
| 投递失败 | `app_event.c:31` 的 `rt_mq_send` 不带超时，返回值被忽略 | 队列满时**静默丢事件**；停止类事件被丢是安全问题 |
| 消费者 | `app_main.c:219` 单线程 `RT_WAITING_FOREVER` | 适合做唯一决策线程；所有状态迁移天然串行 |
| 对象登记 | `obj_desc.c` 只登记 Lift / Swing | SEQ / CALIB / CLUTCH 事件没有归属，需随对应批次补表 |
| 执行器 | `ctrl_executor.c` 有单线程/多线程两套，实际只用单线程 | 暂不启用多线程，避免跨线程改同一状态机 |

**先修三件事，再谈仲裁**：

1. **停止类不丢**：新增 `post_event_stop()`，发送失败置 `s_pending_stop` 原子位。
2. **单写者**：PWM 只有 `swing_axis` 写、阀只有 `valve_tx` 写，其他模块只写意图。
3. **可观测**：每次拒绝记录 `(请求类别, 原因, 当前状态)`，能被 msh 读出。

#### 14.7.3 组件分工

| 组件 | 用途 | 不用于 |
| --- | --- | --- |
| `rt_mq` | 唯一业务事件总线 | — |
| `rt_timer`（soft） | 欠压 10 ms、CAN 发送周期、VOFA 超时 | 不用来给每个去抖/保持各建一个定时器 |
| 50 ms tick | 传感器阈值、限位、2 s 确认、5 s 保持、500 ms 去抖 | 不用来做 30 ms 级判定（精度不够） |
| `rt_sem` | 线程唤醒（CAN 发送已有） | 不用来传事件（会丢计数、无顺序） |
| `rt_mutex` | 存储、参数等非 ISR 共享资源 | 不用来保护状态机（单线程消费即可） |
| `rt_event` | 可做"多个前置条件同时满足"的门禁 | 不做抢占仲裁（表达不了谁先谁后） |
| `rt_mailbox` | — | 不用于事件（只存一个指针，天然丢事件） |
| ISR（20 kHz） | 采样、过流直接切 IDLE、置标志 | 不投队列、不打印、不调状态机 |

#### 14.7.4 输入 → 组件 → 投递

| 输入 | 采集/判定位置 | 判定手段 | 产出 |
| --- | --- | --- | --- |
| ACC 钥匙 | `key_state` 50 ms 轮询 | 500 ms 去抖计数 | `SYS_EVT_ACC_ON/OFF`（边沿） |
| 母线电压 | ADC 20 kHz + 1 ms 平均 | 10 ms 软定时器状态机 | `SYS_EVT_UV_ENTER/RECOVER` |
| 举升传感器 | 50 ms tick 读 ADC | 阈值 + 2 s 进入/恢复计数 | `LIFT_EVT_SENSOR_FAULT/CLEAR` |
| 面板按键 | CAN 接收线程 → `keyboard_sm` | 100 ms 帧、300 ms 超时、同轴互斥 | `LIFT/SWING/ONKEY` 边沿事件 |
| 阀反馈 0E63 | CAN 接收线程 | 500 ms 去抖计数 | `LIFT_EVT_VALVE_FAULT/CLEAR` |
| CAN 静默 | 解析线程心跳 tick | `can_fault_ms`（300） | `CAN_EVT_COMM_FAULT/CLEAR`（新增） |
| 限位/零位 | 50 ms 角度更新 | 越限 + 容差 / 过零检测 | `SWING_EVT_LIMIT_*/ZERO_REACHED` |
| 刹车反馈 | swing 状态机回读 | 解锁/锁止到位 | `SWING_EVT_BRAKE_UNLOCKED/LOCKED` |
| 堵转 | 1 ms 速度环 + 电流 | 多级时间窗 | `STALL` 事件（只上报，急停走安全路径） |
| FOC 过流 | 20 kHz ISR | 硬件级 | ISR 内直接切 IDLE，不经队列 |

原则：ISR 与采集层只写"输入快照"，变化由 50 ms / 1 ms 线程转成边沿事件。

#### 14.7.5 仲裁器接口（纯函数）

```c
typedef enum {
    REQ_CLASS_STOP_ALL = 0,   /* ACC OFF / UV / 过流，最高 */
    REQ_CLASS_CLUTCH,         /* 离合 */
    REQ_CLASS_MANUAL,         /* 手动四向 */
    REQ_CLASS_ONEKEY,         /* 一键三种 */
    REQ_CLASS_CALIB,          /* 校准 */
    REQ_CLASS_NONE
} req_class_t;

typedef struct {
    uint32_t    event;        /* 原始事件，日志原样打印 */
    req_class_t cls;
    int32_t     target_x10;   /* 一键/校准带目标，手动为 0 */
    uint32_t    snapshot_id;  /* 同拍去重用 */
} arb_req_t;

typedef struct {
    uint32_t acc_on, vehicle_started, uv, fault_mask;
    uint32_t angle_valid, ref_valid;
    int32_t  swing_angle_x10, lift_angle_x10;
    uint32_t swing_state, lift_state;
    uint32_t seq_active, calib_active;
} arb_snap_t;

typedef enum { ARB_GRANT, ARB_REJECT, ARB_PREEMPT, ARB_PENDING } arb_decision_t;

typedef struct {
    arb_decision_t decision;
    req_class_t    owner;
    uint32_t       reject_reason;   /* ACC_OFF / NOT_STARTED / UV / FAULT / LIMIT / BUSY / DUPLICATE */
    uint32_t       preempt_evt;     /* 投给被抢占模块的事件 */
} arb_result_t;

arb_result_t arb_submit(const arb_req_t *req, const arb_snap_t *snap);
```

接入位置（`app_main` 事件循环）：

```
收到事件 → 归一化成 arb_req → arb_submit(snap)
    GRANT   → control_object_process(目标对象, 事件)
    REJECT  → 丢弃 + 记录 reject_reason
    PREEMPT → 先向 owner 投 STOP/ABORT，req 进 pending
    PENDING → owner 回 IDLE 后再授予
```

#### 14.7.6 优先级与抢占规则

1. 高类压低类：`STOP_ALL > CLUTCH > MANUAL > ONEKEY > CALIB`，优先级写成常量数组，不写 if 链。
2. 同类不抢占：同键重复、同类重复请求直接 `REJECT`，`reason=DUPLICATE`。
   手动左+右、上+下的互斥仍在键盘层，仲裁只处理跨类。
3. `STOP_ALL` 不等 owner：直接 `GRANT`，清空 pending，向 owner 投强制 STOP。
4. 其他抢占分两步：先投 STOP 并进 pending，owner 回 IDLE 才 `GRANT`；
   **500 ms 未回 IDLE 则强停并记 `preempt_timeout`**（兜底，防止全系统卡死）。
5. 低优先级不排队：被拒即丢弃并计数，避免饿死和高优先级抖动时积压。

#### 14.7.7 单队列 + 停止类不丢

1. 两个入口：
   - `post_event()`：普通事件；`rt_mq_send` 失败只计数。
   - `post_event_stop()`：停止/故障类；发送失败置 `s_pending_stop` 原子位。
2. `app_main` 每轮顺序改为：
   - 先查 `s_pending_stop`，合成为 STOP/FAULT 事件优先处理；
   - 再 `rt_mq_recv` 处理普通事件。
3. `s_pending_stop` 用 32 位掩码按类别置位；可能被 CAN 线程与 50 ms 线程同时置，
   必须用关中断或 `__atomic` 置/清。
4. 队列深度先保持 32，新增 `t_evt` 输出 `used / drops / pending`，跑真实工况后再定是否加深。
5. 20 kHz ISR 仍不进队列：过流在 ISR 直接切 IDLE，只置标志给 50 ms 线程上报。

#### 14.7.8 各模块需要补的状态边

| 模块 | 要补的边 | 说明 |
| --- | --- | --- |
| `swing` | 被抢占 → `LOCKING` → `IDLE` | 复用现有 LOCKING，保证 500 ms 内释放 owner |
| `lift` | 被抢占 → 关阀 → `IDLE` | 可与现有 `LIFT_EVT_SEQ_STOP` 边合并 |
| `seq` | 收到 ABORT 立即停步、关阀 | 不改其他模块内部状态 |
| `calib`（新） | 任何时刻可被 STOP_ALL / 更高类抢占 | 新对象按可抢占设计 |
| `clutch`（新） | 最高业务类，仅低于 STOP_ALL | 新对象按可抢占设计 |

上电自检建议：遍历每个状态的跳转表，缺 STOP 边的状态打印告警，避免抢占卡死。

#### 14.7.11 风险与约束

1. **抢占超时**和**低优先级不排队**必须一起做，否则加入离合/校准后会出现"某模块卡 RUNNING、全系统不可动"。
2. 优先级表扩容时，任何新类都不能插到 `STOP_ALL` 之前。
3. `s_pending_stop` 与 `arb_submit` 都不允许在 20 kHz ISR 内调用。
4. 仲裁器一旦接管 owner，模块不得再自行声明"我在运行"来阻止别人，状态只作为守卫位。
5. 每批新增守护位后，必须回归 `t_arb case` 全场景，避免新守卫把旧路径拒掉。

### 14.8 新增业务代码的放置规划（2026-11-21）

> §14.2/14.3 回答"做什么、按什么顺序"，§14.7 回答"怎么实现"，本节回答
> **"代码加在哪个文件、是改还是新建"**。判断标准只有一条：
> 这个代码属于哪一层；层的归属决定目录，职责的稳定性决定拆不拆文件。

#### 14.8.1 五条放置原则

1. **按层建目录，不按功能名堆放**：仲裁是跨模块决策层，不属于 swing/lift，
   必须独立目录；不要塞进 `app_main.c` 或某个模块的 actions 里。
2. **新对象/新层 → 新目录；既有对象的新规则 → 原地加或同目录拆文件**：
   `lift_sensor.c` 加 2 s 计时是原地改；灯效规则表值得从 `led_tx.c` 拆成
   `led_effect.c`，但不必新建目录。
3. **依赖单向**：`app_main → arbiter → 纯数据`；业务模块**不反向依赖 arbiter**，
   这样仲裁可以整体摘掉回滚，模块也不知道"谁在仲裁"。
4. **定义唯一源**：事件号只在 `app_event.h`；参数只在 `sys_config.c`；
   协议字段只在 `protocol_defs.h`。禁止各模块自定义同名常量。
5. **单文件超 ~500 行按职责拆文件，不拆目录**：传输（收发）、规则（表/纯函数）、
   动作（enter/exit）、命令（msh）四类分开。

#### 14.8.2 目录职责与依赖方向

| 目录 / 文件 | 职责 | 允许依赖 | 不允许 |
| --- | --- | --- | --- |

#### 14.8.5 构建接入（不处理会"代码写了不编译"）

1. **IDE 构建（本工程正式路径）**：`.cproject` 的 `sourceEntries` 是工作区根，
   新增 `applications/<dir>/` 会被自动发现；刷新工程后生成
   `Debug/applications/<dir>/subdir.mk`，无需手工登记。
2. **不要手改 `subdir.mk`**：文件头写明 `Automatically-generated file. Do not edit!`，
   手工改了也会在刷新时被覆盖；同理不要手改 `Debug/*/subdir.mk` 的 `C_SRCS`。
3. **CLI `scons` 只用于语法检查**：`applications/SConscript` 只 `Glob('*.c')` 顶层，
   子目录（swing/lift/sequence/CAN…）不在 SCons 构建范围。因此：
   - 新目录若希望 IDE 的 include 路径稳定，在 `SConscript` 的 `subdirs` 列表追加路径；
   - 正式编译一律走 RT-Thread Studio，不在 CLI 做全量链接。
4. **新增目录的最小登记项**：目录本身 + `subdirs` 追加；不要为新目录写独立
   `SConscript`（本工程既有子目录都没有，保持一致性）。

| 在 `keyboard_sm.c` 里做业务优先级 | 按键层与业务耦合，按键语义难复用 | `arbiter` + 各模块 |
| 在 `app_main.c` 堆 `if/else` 规则 | 事件循环膨胀，无法单测 | 归一化到 `arbiter` / `*_arbit.c` |
| 新建 `business.c` / `utils.c` 万能文件 | 无明确职责，后来者不敢删 | 按层拆 |
| 在 `status_tx.c` 算灯色 | 传输层混入规则 | `led_effect.c` |
| 在 `led_tx.c` 读业务状态机 | 发送层依赖业务 | 由 `led_effect` 传颜色进来 |
| 模块内自定义事件号/参数宏 | 与 `app_event.h`/`sys_config` 冲突 | 统一源 |

#### 14.8.7 可读性验收清单（每批提交前自查）

1. 新增文件能否用一句话说明职责；是否需要"和"才能描述（需要就是职责不单一）。
2. 是否存在反向依赖：`swing` 是否 include 了 `sequence`、模块是否 include 了 `arbiter`。
3. `app_main.c` 本批新增行数是否 <30；超过说明规则放错了层。
4. 跳转表里是否出现阈值、计时、角度判断（出现即应移到上游判定）。
5. msh 是否只通过 getter 读状态，没有直接引用其他文件的 `static` 变量。
6. 新参数是否只在 `sys_config` 定义一次，其他地方只按 ID 读。
7. 纯规则/仲裁文件是否零 RTOS 依赖，能单独用 host gcc 编译。

> 三节关系：§14.2/14.3 = 做什么、顺序；§14.7 = 怎么做（仲裁与组件）；
> §14.8 = 放哪里（目录、文件、构建）。三者共同约束每一批的交付。
